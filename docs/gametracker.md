# GameTracker — the WNY sports event engine

> **GameTracker owns the game. 5StarSportsMedia.com displays it.**
>
> This site never creates a game, edits a score, or keeps a copy of a schedule.
> If a score is wrong it is wrong in GameTracker, and fixing it there fixes it
> everywhere at once — this site, the mobile app, HuddleSphere, team sites,
> league sites and notifications.

```
  Section VI · Monsignor Martin · Arbiter · ScoreBird · ScoreStream · manual admin
                                    │
                                    ▼
                    ┌───────────────────────────────┐
                    │  GameTracker                  │
                    │  gametracker.events           │
                    │  ONE canonical record         │
                    │  upcoming → live → final      │
                    └───────────────────────────────┘
                                    │
        ┌──────────────┬────────────┼────────────┬──────────────┐
        ▼              ▼            ▼            ▼              ▼
   5-Star Sports  GameTracker  HuddleSphere  team & league  notifications
      Media        mobile                       sites
```

Adding a source does not change this site. Adding a sport does not change this
site. Adding a consumer does not change GameTracker.

## 2. The canonical record

One table, `gametracker.events`, for **every** Section VI sport in all three
seasons — and later for college and NFL, unchanged.

It is universal by construction:

- `away_team_name` is **nullable**, because a cross country meet, a swim
  invitational and a wrestling tournament have no away team. Those carry
  `event_name` and a `participants` array instead.
- `period` is **text**, not an integer quarter. Football stores `Q3`, hockey
  `P2`, baseball `Top 5`, volleyball `Set 3`.
- Sport-specific live state goes in **`result_data` (jsonb)** — never a new
  column. Football puts `down`/`distance`/`possession` there, baseball puts
  `inning_half`/`outs`/`balls`/`strikes`, volleyball puts `set_scores`, hockey
  puts `power_play`.
- `scoring_model` on the sport (`team_vs_team` / `meet` / `individual` /
  `bracket`) is what the UI reads to decide how to draw a card. It never
  branches on a sport's name.

**If you find yourself wanting to add a football column, put it in
`result_data`.** That rule is the difference between this and a football app
someone has to convert later.

### Statuses

`upcoming` · `live` · `final` · `postponed` · `cancelled` · `suspended`

One record moves through them. There is no separate "schedule" row and
"scoreboard" row — the schedule row *is* the scoreboard row.

### Uniqueness

`UNIQUE (source, source_event_id)`. This is what makes re-importing safe: the
same file run ten times produces the same games, updated in place.

## 3. Importing a schedule

### Through the admin screen (the normal way)

1. Open `admin-gametracker.html` and sign in as a 5-Star admin.
2. Pick or register the **source** (e.g. `section_vi_2026`).
   Leave *Publish* off to stage a feed — staged games import and are
   inspectable, but never reach the public site or the public API.
3. Upload or paste the JSON/CSV.
4. **Preview.** You get a row-by-row table: what will be added, what will be
   updated (and which fields), what is already current, and what failed and why.
   Nothing has been saved at this point.
5. **Commit.** The games are live on the site immediately. No page is created
   for any game, ever.

### The payload

A JSON array, or `{"events":[…]}`, or `{"games":[…]}`. Both field vocabularies
are accepted, so a football-era file and a universal file both work:

| Universal | Also accepted |
|---|---|
| `source_event_id` | `source_game_id` |
| `event_date` | `game_date`, `date` |
| `home_team_name` | `home_team` |
| `away_team_name` | `away_team` |
| `start_time` | `time` |

```json
[
  {
    "source": "section_vi_2026",
    "source_event_id": "2026-09-04-lancaster-mcquaid",
    "sport": "football",
    "league": "Section VI",
    "season": 2026,
    "region": "WNY",
    "home_team_name": "McQuaid",
    "away_team_name": "Lancaster",
    "event_date": "2026-09-04",
    "start_time": "18:00",
    "timezone": "America/New_York",
    "venue": "McQuaid Jesuit",
    "status": "upcoming"
  }
]
```

**Required:** `source` (or pick one in the UI), `source_event_id`, `sport`,
`event_date`, `home_team_name`. Everything else is optional.

`sport` must be a key in `gametracker.sports` — `football`, `girls-soccer`,
`boys-basketball`, `girls-volleyball`, `boys-ice-hockey`, `wrestling`,
`baseball`, `softball`, `girls-lacrosse`, `boys-cross-country` and so on.
An unknown sport is reported as an error on that row; it never guesses.

CSV works the same way — headers become field names. Start from
`assets/data/gametracker-import-template.csv`. Multi-value `participants` use
`|` as the separator. Quoted fields containing commas are handled.

### What the importer normalizes

- **Times.** `18:00`, `6:00 PM`, `630pm`, `6.30 p.m.`, `1800`, `7` all parse.
  Anything it cannot read becomes `NULL` and the card shows *TBD* — it never
  guesses a kickoff time.
- **Team names.** `Williamsville North High School`, `Williamsville North HS`
  and `williamsville north` all resolve to the same school. Unrecognized
  schools are created automatically and flagged `auto_created` for review;
  further spellings can be mapped with `gametracker_link_alias`.
- **Seasons.** Omitted seasons are derived from the date, with the year rolling
  in July — a February basketball game belongs to the season that began the
  previous autumn.
- **Status.** `scheduled`, `in progress`, `completed`, `ppd` and friends map
  onto the six canonical statuses.

### One protection worth knowing about

A schedule feed **cannot** drag a `live` or `final` game back to `upcoming`.
If the Section VI file is re-synced during Friday night's games, the games in
progress stay in progress. Score sources and admins own status from kickoff on.

## 4. The API

Read endpoints need only the publishable key. They are not 5-Star-specific —
the mobile app and every other consumer call exactly these.

```
POST /rest/v1/rpc/gametracker_events
GET  /rest/v1/rpc/gametracker_events?p_region=WNY&p_sport=football
```

| Param | Example |
|---|---|
| `p_region` | `WNY` |
| `p_sport` | `football`, `girls-soccer`, or a base sport: `soccer` (both genders) |
| `p_gender` | `boys` · `girls` · `coed` |
| `p_league` | `section-vi`, `monsignor-martin`, or `Section VI` |
| `p_section` | `VI` |
| `p_school` | slug or name; matches home **or** away |
| `p_status` | `live` · `upcoming` · `final` · `today` · `tonight` · `postponed` · `all` |
| `p_season_name` | `fall` · `winter` · `spring` |
| `p_date`, `p_date_from`, `p_date_to` | `2026-09-04` |
| `p_season` | `2026` |
| `p_level` | `varsity` · `jv` · `modified` |
| `p_limit`, `p_offset` | paging |

Also: `gametracker_event(p_id)`, `gametracker_filters(p_region, p_season)` —
what is actually loaded, for building filter bars — and
`gametracker_school(p_slug)` for a school page in one round trip.

**Sort order is decided in the database, not the client,** so every consumer
agrees: live first, then upcoming by start time, then postponed, then finals
most-recent-first.

From JavaScript, use the client rather than raw fetch:

```js
const { events, error } = await GameTracker.events({
  region: 'WNY', sport: 'football', league: 'section-vi', status: 'tonight'
});
```

### Writes

All admin-gated on `public.is_admin()` — the same gate `admin.html` uses. No
second identity system was introduced.

| Function | Purpose |
|---|---|
| `gametracker_import(payload, dry_run, source)` | preview / commit an import |
| `gametracker_update_live(id, status, home_score, away_score, period, clock, result_data, score_source)` | move a game's live state |
| `gametracker_save_source(...)` | register a feed; flip its publish gate |
| `gametracker_link_alias(alias, school_slug)` | map a team-name spelling |
| `gametracker_admin_events(...)` | inspect staged (unpublished) feeds |
| `gametracker_delete_event(id)` | remove one mistaken row |

## 5. The publish gate

`gametracker.sources.publish` is the line between *imported* and *on the site*.
The public API returns events from published sources only.

This exists so a feed can be loaded, inspected and exercised end to end without
a single unverified game appearing in front of a reader. The `selftest` source
is permanently unpublished and is what the pipeline is tested against.

## 6. Adding a source (Arbiter, ScoreBird, ScoreStream, a new league)

Nothing in this site changes. The whole job is:

1. Register the source (admin screen, or `gametracker_save_source`).
2. Write a shim that turns that feed into the JSON array above.
3. Call `gametracker_import` — or, for live scores, `gametracker_update_live`.

The shim is the *only* new code. It does not touch the schema, the API, the UI,
or any consumer. That is the entire point of the layer.

Leagues are data too: a new league is a row in `gametracker.leagues`, not a
schema change. Section VI is the first major content source, not a built-in
assumption.

---

## 7. Notification readiness (structure only — nothing is sent yet)

Every state change writes a row to `gametracker.event_log`, emitted by a
database trigger rather than by the importer. That matters: the importer, a
future live-score adapter and a manual admin correction all produce the same
stream without any of them knowing about it.

`game.created` · `game.updated` · `game.started` · `score.updated` ·
`game.final` · `game.cancelled` · `game.postponed`

`delivered_at` is `NULL` on every row. A future notification worker claims rows
through that column. **No notification system is built and nothing is sent.**

---

## 8. Connecting a live-score source — the exact next step

`gametracker_update_live` is already built, tested and admin-gated. To wire
ScoreBird or ScoreStream in:

1. Register the source with `kind: 'score'` and the matching `adapter`.
2. Map that feed's game identifier to a GameTracker event. If the score feed
   also supplies the schedule, import through the same `source` and the ids
   line up for free. If it does not, add a crosswalk keyed on
   (date, sport, home team, away team) resolved through
   `gametracker.resolve_school`.
3. On each poll or webhook, call `gametracker_update_live` with the score,
   period, clock and status, plus any sport-specific state as `result_data`.
4. Nothing else. The scoreboard, the homepage module, school pages and sport
   pages all update on their own, because they are reading the same record the
   schedule created.

Until such a source exists, an admin moves a game with the same call. The site
does not pretend to have live data it does not have: with no live games, the
LIVE tab says so plainly.
